# Verstka — архитектура сервиса «Цифровой дизайнер презентаций»

Дата: 2026-09-21. Статус: утверждён. Кейс № 4 ЛЦТ 2026 от VK Tech.

## 1. Цель и рамки

**Цель.** Сервис получает произвольный PPTX (шаблон или прошлую презентацию) и бриф, извлекает из PPTX дизайн-систему и паттерны слайдов, строит 10–15 слайдов (или столько, сколько попросил пользователь) в трёх визуально разных вариантах вёрстки, проверяет результат аудитом, объясняет свои решения в чате и экспортирует в PPTX, PDF и HTML. Всё за ≤5 минут на колоду.

**Принцип.** «Читать чужой шаблон как набор правил». Источник правил — весь файл: мастера, макеты и обычные слайды. Никаких зашитых сценариев под три выданных шаблона: на финале будет неизвестный PPTX, возможно нарисованный вручную поверх пустых слайдов без макетов.

**Что входит в объём до 30 сентября.**
- Парсер шаблона: токены, паттерны, компоненты, ассеты, текстовые правила.
- Планировщик контента с реестром фактов и извлечением данных для диаграмм.
- Матчер паттернов с объяснениями.
- Два рендерера (клон образца, синтез из токенов), нативные диаграммы и таблицы, иконки.
- Аудит: детерминированные проверки и VLM-проверки, автофикс, выбор фиксов пользователем.
- Три варианта по оси «композиционная стратегия».
- Экспорт PPTX, PDF, HTML.
- Реестр версионируемых скиллов и агентов, манифест запуска.
- FastAPI, React-чат с рабочей областью, CLI с конфиг-файлом.
- Документы README, ARCHITECTURE, MODELS, AUDIT; 9 демонстрационных колод; видео.

**Не входит.** Генерация изображений text-to-image (задача со звёздочкой для топ-10, с 15 октября), мобильные интерфейсы, многопользовательская авторизация, откат версий скиллов через интерфейс (только просмотр и сравнение).

**Ограничения из ТЗ и Q&A.** Только открытые веса Apache 2.0 или MIT, ≤35B на модель, закрытые API запрещены и на прототипе. На финале все модели через инференс VK (Qwen3.8-27B), фронт и бэкенд могут быть свои. PPTX только с нативными редактируемыми объектами; растровый слайд не засчитывается. Промпты и конфиги скиллов лежат отдельными файлами. Стек Python и TypeScript, десктопный веб.

## 2. Обзор архитектуры

Пайплайн из семи слоёв с JSON-контрактами между ними плюс три сквозных сервиса (провайдеры моделей, реестр скиллов, оркестратор). Каждый слой можно запустить и протестировать отдельно через CLI.

```
PPTX ──► Ingest ──► Template Analysis ──► manifest.json
                                              │
brief ──► Content Planning ──► outline.json ──┤
                                              ▼
                              Layout Matching ──► layout_plan.json
                                              ▼
                              Rendering (clone | synth) ──► deck.pptx + deck_ir.json
                                              ▼
                              Audit ──► audit_report.json ──► autofix loop (≤2)
                                              ▼
                              Export ──► .pptx .pdf .html + thumbs
```

Сквозные сервисы: `providers` (LLM/VLM/T2I), `skills_registry` (версии скиллов и агентов, `run_manifest.json`), `pipeline` (задачи, прогресс, кэш, бюджет времени, параллелизм).

## 3. Слои пайплайна

### 3.1 Ingest

Вход: путь к PPTX. Выход: рабочая папка `workspace/templates/<sha256>/` с распакованным пакетом, `slides/*.png` (рендер через LibreOffice → PDF → `pdftoppm`, 150 dpi для анализа и 72 dpi для превью), `media/`, метаданные: размер слайда в EMU, порядок слайдов, связи слайд → макет → мастер → тема, список встроенных шрифтов.

Правила: отпечаток файла по sha256, повторная загрузка того же файла берёт кэш. Прошлая презентация без макетов обрабатывается тем же путём. Битые слайды не останавливают загрузку, они помечаются и пропускаются.

### 3.2 Template Analysis

Вход: рабочая папка Ingest. Выход: `manifest.json` (схема `TemplateManifest`), `assets/`, `thumbs/`.

**Токены (`tokens`).**
- `colors`: цвета из заливок, текста, линий всех слайдов, макетов и мастеров, кластеризованные с допуском ΔE; для каждого частота и контексты (фон, текст, заливка фигуры, линия). Роли: `background.light`, `background.dark`, `surface`, `text.primary`, `text.secondary`, `accent.1..n`, `semantic.positive`, `semantic.negative` (если детектируются), плюс отображение на схему темы.
- `typography`: семейства по частоте в ранах (не из темы, тема часто врёт: во всех трёх шаблонах VK тема пишет Arial, а раны используют Play); кегли, кластеризованные в шкалу с ролями `display`, `h1`, `h2`, `body`, `small`, `caption`; жирность, межстрочный интервал, выравнивание по умолчанию.
- `spacing`: безопасная область (объединение bbox контентных фигур без хрома), сетка колонок из повторяющихся координат x, типичные зазоры между карточками.
- `shapes`: распределение радиусов скругления, толщины и цвета обводок, наличие теней, стиль заливки карточек.
- `chrome`: фигуры, стоящие в одном bbox (допуск 1%) не менее чем на 40% слайдов: логотипы, колонтитулы, номера, декоративные узоры. Хром копируется на каждый сгенерированный слайд и не должен сдвигаться.
- `backgrounds`: семьи слайдов (светлая, тёмная, акцентная) с типом фона (сплошной, градиент, картинка) и ссылками на ассеты.
- `slide_size`: ширина и высота в EMU.

**Паттерны (`patterns`).** Каждый слайд-образец → паттерн. Дубликаты (одинаковая геометрия и роли) схлопываются. Поля:
- `id`, `source_slide`, `kind` из закрытого списка: `title`, `section`, `agenda`, `bullets`, `cards`, `two_column`, `big_number`, `stat_row`, `comparison`, `timeline`, `process`, `table`, `chart`, `image_text`, `team`, `quote`, `code`, `mockup`, `thanks`, `freeform`.
- `family`: светлая или тёмная.
- `slots`: `{id, role, bbox, style_ref, capacity{max_chars, max_lines}, group_id}`; роли: `title`, `subtitle`, `body`, `bullet_list`, `card_title`, `card_body`, `number`, `number_label`, `caption`, `image`, `icon`, `decoration`, `chrome`.
- `repeat_groups`: `{id, member_shape_ids, min_n, max_n, axis(row|column|grid), gap, cell_bbox}` — группы из k похожих фигур, выровненных по сетке. `max_n` считается из свободного места вдоль оси.
- `decor_assets`: картинки, признанные декором (иллюстрации), с флагом «можно заменить».
- `quality`: балл пригодности паттерна (штраф за lorem ipsum, за неразобранные группы, за перегруз).
- `thumbnail`: путь к PNG.

Классификация ролей и `kind` — ансамбль из трёх сигналов, результат и уверенность каждого сохраняются в манифесте:
1. Геометрические эвристики: относительное положение, размер, кегль, число строк, повторяемость, наличие картинки.
2. Скилл `slide_classifier` (LLM): компактный JSON фигур (координаты в процентах, размеры, кегли, первые 40 символов текста) → роли и `kind` по JSON-схеме.
3. Скилл `slide_vision_check` (VLM): PNG слайда → назначение слайда и подтверждение `kind`. Расхождение с LLM снижает `quality` и помечает паттерн для ручной проверки в инспекторе.

**Компоненты (`components`).** Спецификации, извлечённые из групп: `card` (заливка, радиус, отступы, стиль заголовка и текста), `bullet_item` (маркер, отступ, интервал), `number_callout` (кегль, цвет, подпись), `icon_chip` (фон, размер, цвет иконки), `divider`, `table_style` (шапка, зебра, границы, выравнивание чисел), `chart_style` (цвета рядов по порядку акцентов, сетка выключена, подписи данных, шрифт легенды).

**Правила (`style_rules`).** Скилл `rule_harvester` (LLM) вычитывает текст слайдов и достаёт написанные дизайнером правила (например, в VK Education: заголовки слева, таблицы без заливок, столбики предпочтительнее круговых, точки навигации на разделителях). Плюс производные правила из статистики (доля выравнивания влево > 80% → правило «текст влево»).

**Ассеты (`assets`).** Все картинки из медиа: размер, прозрачность, тип (`illustration`, `icon`, `photo`, `mockup`, `logo`, `pattern`) по эвристике и VLM-тегу, где использованы. Листы иконок (десятки мелких картинок на одном слайде) нарезаются в отдельные ассеты с тегами.

### 3.3 Content Planning

Вход: бриф (текст или markdown, опционально таблицы данных), `audience`, `purpose` (`feature`, `product`, `project`, `initiative`), `constraints` (число слайдов, язык, тон), `strategy` варианта, сводка манифеста (какие `kind` доступны). Выход: `outline.json` (`DeckOutline`).

Скиллы:
- `data_extractor`: находит в брифе числа, ряды, таблицы → `facts[]` с `{id, value, unit, label, source_span}` и `series[]` для диаграмм.
- `outline_planner`: строит слайды `{id, kind, section, headline, body{bullets[], paragraphs[], items[{title, text, icon_hint}], numbers[fact_id], table{cols, rows}, chart{type, series_ref, categories, unit}, quote, image_hint}, notes, fact_refs[]}`. Заголовок обязан быть выводом, а не темой. Соблюдает число слайдов из ограничений, нарративную дугу (от общего к частному или наоборот по типу брифа), лимиты плотности из аудита (≤6 буллетов, ≤15 слов в буллете, таблица ≤7×5, ≤5 рядов).
- `fact_checker`: сверяет все числа и утверждения плана с `facts[]`; несовпадения возвращаются планировщику одной итерацией, остаток помечается для аудита.

Три варианта получают три плана из одного `facts[]`: содержание одно, группировка и порядок разные (это прямо разрешено организаторами).

### 3.4 Layout Matching

Вход: `outline.json`, `manifest.json`, `strategy`. Выход: `layout_plan.json` (`LayoutPlan`): для каждого слайда `{outline_id, mode: clone|synth, pattern_id?, composition?, fit{items: n_needed/n_available, text_ratio}, score, reasons[]}`.

Скоринг детерминированный, веса лежат в `configs/strategies.yaml`:
- совместимость `kind` (таблица соответствий с запасными вариантами, например `stat_row` → `big_number` → `cards`);
- попадание числа пунктов в `[min_n, max_n]` группы;
- отношение длины текста к ёмкости слотов (подгонка кеглем допускается только внутри шкалы шаблона);
- совпадение семьи (светлая или тёмная) с соседями;
- штраф за повтор паттерна в окне из трёх слайдов;
- веса стратегии варианта.

Если лучший балл ниже порога, слайд получает `mode: synth` и `composition` из фиксированного набора: `grid_cards(n)`, `stat_row(n)`, `two_column`, `chart_left_text_right`, `table_full`, `timeline(n)`, `process(n)`, `bullets`. Каждое решение снабжается `reasons[]` на человеческом языке для чата.

### 3.5 Rendering

Вход: `layout_plan.json`, `outline.json`, `manifest.json`. Выход: `deck.pptx` на пакете шаблона (мастера, макеты, тема, встроенные шрифты сохраняются) и `deck_ir.json` (`DeckIR`: единая внутренняя модель — слайды, элементы с типом, bbox, ссылками на токены, ранами текста; строится парсером из готового PPTX, поэтому одинаково описывает оба пути рендера).

**Клон-рендерер.** Копирует часть слайда-образца со всеми связями в новый пакет (регистрация в `presentation.xml`, `[Content_Types].xml`, rels). Затем: текст в слоты с сохранением свойств первого рана; один абзац на пункт; повторяющиеся группы обрезаются (лишние члены удаляются) или дублируются вдоль оси до `max_n`; слоты картинок получают ассет шаблона по тегу или остаются с декором; остатки текста-заглушки удаляются; текст подгоняется по реальным метрикам (Pillow и TTF: Play из Google Fonts в комплекте, метрически совместимые замены для Arial и Calibri), шаг уменьшения кегля только по шкале шаблона; если не влезает, текст возвращается скиллу `text_condenser` на сокращение.

**Синтез-рендерер.** python-pptx на пустом макете мастера шаблона с сохранённым фоном и хромом; композиция по сетке из компонентов и токенов.

**Диаграммы и таблицы.** Всегда нативные объекты python-pptx. Диаграммы: bar, column, line, area, pie, doughnut; цвета рядов из акцентов, сетка выключена, подписи данных, единицы в легенде или подписи, шрифт из токенов. Таблицы: стиль из `table_style`, текст влево, числа вправо, единый формат округления, минимальные границы.

**Иконки.** Сначала ассеты шаблона по тегу (скилл `icon_matcher`), иначе набор Tabler Icons (MIT) как SVG, перекрашенный в акцент; SVG допустим как отдельный передвигаемый объект, но презентация не должна состоять из SVG.

Отказоустойчивость: клон не удался → синтез для этого слайда; синтез не удался → паттерн `bullets`. После каждого слайда проверка валидности XML.

### 3.6 Audit

Вход: `deck.pptx`, `deck_ir.json`, PNG слайдов, `manifest.json`, `outline.json`. Выход: `audit_report.json` (`AuditReport`): `issues[{id, slide, check_id, severity: error|warn|info, kind: deterministic|model, message, bboxes[], suggestion, autofix{available, action}}]`, `summary{errors, warnings, model_flags, score}`.

**Детерминированные проверки (`audit/checks/*.py`, по одной на файл).**
- Вёрстка: элемент за границей слайда; наложение двух текстовых блоков (IoU выше порога, слои с декором исключены); переполнение текстового блока (по метрикам); текст обрезан краем; выход в поля; блок не на сетке шаблона; картинка растянута (соотношение сторон отличается от исходного).
- Шаблон: шрифт не из шаблона или более двух гарнитур; кегль не из шкалы (допуск ±0.5 пт); цвет не из палитры (допуск ΔE); слайд не ссылается на макет шаблона; хром сдвинут; контраст текста к фону ниже 4.5:1 по WCAG.
- Плотность: более 6 буллетов; буллет длиннее 15 слов; таблица больше 7 строк или 5 колонок; более 5 рядов; заполнение слайда меньше 25% или больше 75%.
- Целостность: файл открывается python-pptx и рендерится LibreOffice; заглушки (lorem, XXX, TODO, «вставьте», «Заголовок в две или в одну строчку»); пустой слайд или только заголовок; слайд-картинка; у диаграммы нет подписей осей, единиц или легенды; два слайда дублируют друг друга (сходство текста).

**Модельные проверки.** Скилл `slide_content_audit` (VLM): PNG слайда плюс контекст плана → 11 вопросов из приложения к ТЗ с ответом да/нет, уверенностью и цитатой-обоснованием. Скилл `deck_coherence_audit` (LLM): последовательность заголовков → связность соседних слайдов и колоды в целом.

**Автофикс.** Не более двух итераций, только детерминированные классы: ужать или сократить текст, перегруппировать элементы, перевыбрать паттерн, привести цвет к ближайшему из палитры, заменить шрифт на шаблонный, вернуть элемент в границы. В интерфейсе пользователь отмечает, что исправлять; в CLI флаг `--autofix`. Применённые фиксы записываются в `run_manifest.json`.

### 3.7 Export

PPTX — уже нативный результат рендера. PDF — LibreOffice headless. HTML — собственный рендерер из `DeckIR`: один файл, слайды как секции с абсолютным позиционированием, шрифты встроены base64, картинки inline, таблицы как `<table>`, диаграммы как inline SVG, навигация клавиатурой. PNG-превью для интерфейса.

## 4. Три варианта: ось «композиционная стратегия»

Все три варианта подчиняются одним токенам и одному аудиту. Различаются инструкцией планировщику и весами матчера (`configs/strategies.yaml`).

| Вариант | Планировщик | Матчер |
|---|---|---|
| `structured` («Структурный») | одна мысль на слайд, разделители секций, порядок от общего к частному | максимум клонов паттернов, приоритет `bullets`, `cards`, `section` |
| `visual` («Визуальный») | выводы в начале, числа выделены, тезисы короткие, подсказки иконок и иллюстраций | приоритет `big_number`, `stat_row`, `chart`, `image_text`, иконки-чипы |
| `compact` («Компактный») | объём на треть меньше, смежные тезисы объединены, без разделителей | приоритет `two_column`, `comparison`, `table`, плотные композиции |

Обоснование выбора оси хранится в ARCHITECTURE.md: ось меняет и порядок, и макеты, и способ подачи данных, при этом остаётся проверяемой аудитом.

## 5. Модели и провайдеры

`configs/models.yaml` задаёт роли → бэкенд, модель, параметры:
- `llm` и `vlm`: `qwen/qwen3.8-27b` (Apache 2.0, мультимодальная, контекст до 1M на OpenRouter). Прототип: OpenRouter. Финал: та же модель на инференсе VK через OpenAI-совместимый `base_url`. Thinking выключен для скорости, включается только у `outline_planner`, если укладываемся в бюджет.
- Запасной `llm`: `qwen/qwen3.6-27b` или Qwen3-32B (Apache 2.0).
- `t2i` (после 15 октября): Z-Image-Turbo (6B, Apache 2.0) по умолчанию, Qwen-Image-2512 (20B, Apache 2.0) как качественный вариант; палитра шаблона задаётся промптом и постобработкой.
- `mock`: детерминированные ответы из фикстур для тестов.

Слой `providers`: OpenAI-совместимый клиент, структурированный вывод по JSON-схеме с валидацией pydantic и до двух повторов, ретраи с экспоненциальной задержкой, учёт токенов и стоимости на запуск, тайм-ауты на вызов.

## 6. Скиллы, агенты, версионирование

`skills/<name>/skill.yaml`: `name`, `version` (semver), `role` (`llm`|`vlm`), `prompt_files[]`, `output_schema`, `params`, `changelog`. Промпты в `skills/<name>/prompts/*.md`. `agents/<name>.yaml`: последовательность шагов и используемых скиллов. Реестр загружает, валидирует и считает sha256 содержимого каждого скилла.

`run_manifest.json` на каждую генерацию: версии и хэши скиллов и агентов, модели и провайдер, параметры, хэш шаблона и брифа, стратегии, время по стадиям, стоимость, применённые фиксы, сводка аудита, версия кода (git commit). Интерфейс показывает «сгенерировано скиллами …» и сравнивает два запуска: что изменилось в скиллах и как изменился результат. Версии скиллов фиксируются git-тегами.

Список скиллов первой версии: `slide_classifier`, `slide_vision_check`, `rule_harvester`, `asset_tagger`, `data_extractor`, `outline_planner`, `fact_checker`, `text_condenser`, `icon_matcher`, `slide_content_audit`, `deck_coherence_audit`, `chat_agent`.

## 7. Оркестратор, API, интерфейс, CLI

**Оркестратор (`pipeline`).** Задача = последовательность стадий с событиями прогресса (SSE). Кэш: анализ шаблона по хэшу, планы по хэшу брифа и стратегии. Параллелизм: три варианта рендерятся параллельно, VLM-проверки конкурентно (лимит из конфига). Бюджет: мягкие дедлайны стадий, при превышении необязательные стадии (VLM-аудит) пропускаются с пометкой в манифесте. Отказ провайдера → запасная модель → деградация до детерминированного аудита.

**API (FastAPI).**
- `POST /api/templates` (загрузка, запуск анализа), `GET /api/templates/{id}` (манифест, превью, паттерны).
- `POST /api/generations` `{template_id, brief, audience, purpose, constraints, strategies[], autofix}` → `job_id`; `GET /api/jobs/{id}/events` (SSE); `GET /api/generations/{id}` (варианты, PNG, аудит, манифест); `POST /api/generations/{id}/fixes` (выбранные issue → новая ревизия); `GET /api/generations/{id}/export?format=pptx|pdf|html&variant=…`.
- `POST /api/chat/{session}`: сообщения агенту; скилл `chat_agent` выбирает действие (анализ, план, генерация, аудит, фикс, объяснение) и стримит ответ.
- `GET /api/skills`: реестр и версии; `GET /api/runs/{a}/diff/{b}`: сравнение манифестов.

**Интерфейс (React + Vite + TypeScript, Tailwind, shadcn/ui, только десктоп).** Слева чат с агентом: загрузка шаблона и брифа в чат, агент рассказывает шаги, объясняет выбор макетов и находки аудита, задаёт уточняющие вопросы только при необходимости. Справа рабочая область с вкладками: «Шаблон» (токены, галерея паттернов с превью и уверенностью классификации), «План» (редактируемые заголовки и пункты до рендера), «Варианты» (три вкладки, плёнка слайдов, крупное превью с рамками проблем аудита), «Аудит» (проблемы по слайдам, чекбоксы «исправить», кнопка «исправить всё детерминированное»), «Экспорт», «Запуск» (версии скиллов, стоимость, время, сравнение с предыдущим запуском).

**CLI (`verstka`).** `verstka analyze template.pptx`, `verstka generate --config run.yaml` (шаблон, бриф, ограничения, стратегии, папка вывода → 3 варианта, аудит, экспорт), `verstka audit deck.pptx --template <id>`, `verstka export`. Конфиг-файл = воспроизводимый запуск для финала.

## 8. Тестирование и оценка

- Юнит-тесты: парсер на фикстурах (три шаблона плюс синтетическая колода без макетов); точность классификации ролей и `kind` на размеченном подмножестве около 40 слайдов; детекция повторяющихся групп; измерение текста; каждая детерминированная проверка аудита с позитивной и негативной фикстурой; валидность XML диаграмм и таблиц; открываемость через LibreOffice; рендер-раундтрип (`DeckIR` из сгенерированного PPTX совпадает с планом).
- Интеграция: каждый шаблон × два брифа × три варианта; после автофикса ноль детерминированных ошибок; время < 5 минут; стоимость и токены в отчёте.
- Отложенный набор: шаблон ЛЦТ 2026 и вручную нарисованная колода без макетов; на них не тюнимся, они играют роль неизвестного шаблона в CI.
- Демонстрационные брифы: три (фича, продукт, инициатива) с числовыми таблицами; из них собираются 9 колод для сдачи и видео.
- AUDIT.md перечисляет проверки, их тип и покрытие тестами.

## 10. Порядок сборки

1. Скелет: схемы, провайдеры с mock, ingest с рендером в PNG, каркас CLI.
2. Анализ шаблона: токены, паттерны, компоненты, ассеты, правила; галерея паттернов.
3. Планировщик, матчер, клон-рендерер, диаграммы и таблицы → первая колода.
4. Детерминированный аудит, автофикс, экспорт PDF и HTML.
5. Синтез-рендерер, три стратегии, VLM-аудит.
6. API, веб-чат, реестр скиллов и сравнение запусков.
7. Документация, 9 колод, видео, полировка.

Каждый шаг заканчивается работающим артефактом, который можно показать.

## 11. Риски и меры

| Риск | Мера |
|---|---|
| Классификация ролей на произвольной колоде ошибается | ансамбль трёх сигналов, уверенность в манифесте, ручная проверка в инспекторе, запасной путь синтеза |
| Подгонка текста без точных метрик шрифта | Play в комплекте, метрически совместимые замены, консервативная ёмкость, скилл сокращения |
| Хирургия повторяющихся групп ломает вёрстку | только удаление лишних и дублирование вдоль оси; иначе синтез |
| 5 минут с VLM-аудитом | параллелизм, кэш анализа, деградация до детерминированных проверок |
| Провайдер недоступен | ретраи, запасная модель, mock для тестов |
| Неизвестный шаблон на финале без макетов | парсер опирается на слайды, а не на макеты; отложенный набор в CI |
