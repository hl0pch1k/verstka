# MODELS — модели, роли, требования

Все модели — только с открытыми весами и лицензией Apache 2.0 / MIT: для текста и зрения не больше 35B параметров, для изображений — не больше 20B (задача со звёздочкой, п. 3.1 ТЗ). Закрытые API не используются нигде, в том числе на прототипе. Лимит считается для каждой модели отдельно — так ответили организаторы на встрече, — число моделей не ограничено.

Профиль моделей выбирается по ключам в `.env`. С `VK_INFERENCE_API_KEY` и `VK_PROJECT_ID` работает **профиль VK** ([`configs/models.vk.yaml`](configs/models.vk.yaml), раздел «Финал: инференс VK»): текст и чтение изображений — Qwen3.8-27B (`qwen38-27b-fp8`) на инференсе VK; если VK не отвечает (недоступен, «500 congested upstream», таймаут), в том же запросе отвечает та же Qwen3.8-27B на Polza, затем Qwen3.6-27B на Polza (нужен `POLZA_API_KEY`); изображения — Z-Image через Polza (`POLZA_API_KEY`). Без ключей VK работает **профиль Polza** ([`configs/models.yaml`](configs/models.yaml)): все три модели — через один сервис, [Polza.ai](https://polza.ai) (OpenAI-совместимый API, оплата в рублях, один ключ `POLZA_API_KEY` в `.env`).

| Роль | Модель | Id на Polza | Лицензия | Параметры | Где используется | Веса |
|---|---|---|---|---|---|---|
| `llm`, `vlm` — основная (профиль Polza и VK) | Qwen3.8-27B | `qwen/qwen3.8-27b` | Apache 2.0 | 27,8B, dense, понимает изображения | классификация слайдов шаблона, извлечение правил, реестр фактов, план колоды, тексты слайдов, сокращение, проверка фактов, связность, чат-агент, связка колоды из данных, понимание целей брифа над файлами с данными; по картинке — тип слайда, теги ассетов, 11 вопросов валидации контента, страницы PDF-брендбука | https://huggingface.co/Qwen/Qwen3.8-27B |
| `llm`, `vlm` — запасная (профиль Polza) | Qwen3.6-27B | `qwen/qwen3.6-27b` | Apache 2.0 | 27,8B, dense, понимает изображения | то же, когда основная не может ответить (см. «Основная и запасная») | https://huggingface.co/Qwen/Qwen3.6-27B |
| `llm`, `vlm` — профиль VK | Qwen3.8-27B (fp8) | `qwen38-27b-fp8` на инференсе VK | Apache 2.0 | 27,8B, dense, понимает изображения | то же, что у основной; запасные — те же Qwen3.8-27B и Qwen3.6-27B на Polza | https://huggingface.co/Qwen/Qwen3.8-27B |
| `t2i` — изображения в слайдах | Z-Image | `tongyi-mai/z-image` | Apache 2.0 | 6,15B + кодировщик текста Qwen3-4B ≈ 10B | изображения на местах, которые автор описал в тексте, в палитре шаблона | https://huggingface.co/Tongyi-MAI/Z-Image |

**Почему эти.** Qwen3.8-27B — та самая модель, которую VK предоставляет финалистам: промпты отлаживались на Qwen3 (Qwen3.8-27B до 24.09, Qwen3-32B 25–29.09), на Polza проверены 06.10, и в финале она же работает на инференсе VK ([`configs/models.vk.yaml`](configs/models.vk.yaml)). Запасная — Qwen3.6-27B, предыдущая версия той же линейки: по индексу Artificial Analysis она сильнее Gemma 4 31B (37 против 29), отвечает в том же формате и тоже читает картинки. Qwen-Image для изображений не взята: у неё 20,4B параметров плюс 8,3B кодировщика текста — больше лимита 20B. Qwen-Image-2.1 выходит за лицензионное требование (исследовательская лицензия Qwen), Qwen Image 2 / 3 / Max — закрытые. Qwen3.5 / 3.6-35B-A3B — 35,95B, больше 35B.

## Сервис API и настройки
Таблица описывает профиль Polza (`configs/models.yaml`); чем отличается профиль VK — в разделе «Финал: инференс VK».

| Параметр | Значение |
|---|---|
| API | Polza.ai, `https://polza.ai/api/v1`, `Authorization: Bearer $POLZA_API_KEY` |
| Хосты модели | Polza сама выбирает хост модели и при сбое переходит к другому. Хосты с 4-битными весами (`…/fp4`) исключены (`exclude_quantizations: [fp4]` → `provider.ignore`): на них Qwen портила JSON. Список берётся из открытого каталога Polza (`GET https://api.polza.ai/v1/models/{id}`, без ключа) при первом запросе к модели и перечитывается раз в 6 часов; если каталог недоступен, Polza выбирает хост сама, повторная попытка — через 10 минут |
| Рассуждения | выключены: `reasoning: {effort: none}` (поле `reasoning_effort` на верхнем уровне Polza игнорирует). Проверено вживую: 0 токенов рассуждений |
| Формат ответа | `json_mode: false`: схема JSON — в промпте скилла, ответ разбирается и проверяется схемой; обрезанный ответ запрашивается ещё раз короче, невалидный — с текстом ошибки |
| `temperature` | своя у каждого скилла (`params.temperature` в `skills/<имя>/skill.yaml`): 0 — извлечение фактов и проверки, 0,1 — классификация, теги, правила, сокращение, критик, проверка по картинке, 0,2–0,3 — сюжет, план, слайды, тексты автора, промпты изображений |
| Тайм-аут и повторы | 120 с на запрос, до 3 попыток; ошибка, которую повтор не исправит (400, 413, отказ модерации, а у Polza ещё 402 без резерва, 401, 403, 404), сообщается сразу, а настройки запроса (`reasoning`, `provider`) при этом не снимаются |
| Параллельность | до 4 вызовов одновременно на шаг |
| Бюджет времени модели | 210 с на генерацию трёх вариантов; после него вёрстка, проверка и экспорт идут без модели и укладываются в 5 минут |
| Стоимость | Polza возвращает стоимость каждого ответа в рублях (`usage.cost_rub`). Verstka складывает её в `run_manifest.json`: `usage.cost_rub` — все вызовы моделей генерации (план, тексты, проверки), по скиллам — `usage.by_skill`; `planner.agent.cost_rub` — вызовы агента; `pictures.cost_rub` — изображения варианта (три варианта делят одни и те же изображения, они оплачены один раз); у каждого изображения — `images/*.json` → `cost_rub`. Ошибка ничего не стоит. Сервис, который стоимость не сообщает (инференс VK в финале), оставляет поле пустым (`null`), а не «0 ₽» |

Проверено на живом ключе 06.10.2026: обе текстовые модели отвечают JSON за 1,3–1,4 с и читают текст с картинки; без исключения хостов Polza однажды отправила запрос на хост с fp4 (Darkbloom); Z-Image рисует 1280×720 (16:9) за 8,7 с, 1,40 ₽ за изображение.

## Взгляд дизайнера (`vlm`, Verstka 3.0)

После аудита и автофикса каждого варианта модель с компьютерным зрением — та же Qwen3.8-27B (запасная Qwen3.6-27B тоже видит картинки) — смотрит на картинку каждого готового слайда (скилл `slide_design_review`), а слайд с серьёзной проблемой собирается заново и сравнивается со старым рядом (`slide_design_compare`): новая вёрстка остаётся, только если детерминированный аудит не стал хуже, слайд заметно изменился и модель выбрала новую в обоих порядках пары ([`verstka/audit/eyes.py`](verstka/audit/eyes.py), [`configs/eyes.yaml`](configs/eyes.yaml)). Проверено вживую 07.10: модель нашла четыре слова, разорванных посередине в узких карточках (Marketing Report), пустую строку сетки под плашкой и сетку 2×2 с пустой половиной слайда («Классика»), пропустила чистый слайд VK Tech и в обоих порядках пары выбрала вёрстку без разрывов. Один взгляд — 2–7 с и 0,03–0,11 ₽ (≈ 940 токенов на вход: картинка и промпт), сравнение — около 3 с и 0,03–0,05 ₽ (два на пересобранный слайд, параллельно); на колоду из 14 слайдов в трёх вариантах — около 40 взглядов, ≈ 3 ₽. Проверка варианта идёт, пока собирается следующий, и добавляет к сборке 40–60 с (Marketing Report: 79 → 123 с, «Классика»: 70 → 130 с при трёх пересобранных слайдах). Включается вместе с моделью текста; «Улучшить готовую» включает её и при тексте, разложенном как написан (`eyes: true` в запросе).

## Изображения внутри слайдов (`t2i`)

Z-Image на Polza через Media API: `POST /media {model, input: {prompt, aspect_ratio}}`. Ответ — либо готовая ссылка на изображение, либо задача: тогда Verstka опрашивает `GET /media/{id}` раз в 3 с, пока статус не станет `completed` (или `failed` / `cancelled`), не дольше тайм-аута (90 с) и бюджета генерации; неудачный запрос статуса (404, 5xx, тайм-аут) просто повторяется при следующем опросе — задача одна и оплачивается один раз. Изображение скачивается из CDN Polza. Z-Image принимает пропорции 1:1, 4:3, 3:4, 16:9, 9:16 и промпт до 1000 символов; seed не принимает — новое изображение того же места получается новым запросом.

Как строится изображение:
Где рисуются картинки ([`planning/pictures.py`](verstka/planning/pictures.py)), когда «С изображениями» включено:
- места, которые автор описал в тексте («[Место под изображение: …]»), и картинки, которые человек попросил в правке или в Помощнике («добавь картинку», «создай изображение»);
- сверх них — короткие слайды, заголовок которых называет то, что можно увидеть (склад, сканер, приложение, озеро): у каждого свой предмет, не больше примерно одной картинки на 4 слайда, без повторов; шаги, хронология, две колонки и три карточки картинку не получают;
- в колоде не меньше 1 картинки (до 7 слайдов) или 2 (от 8): если предметных слайдов не хватает, на самых свободных коротких слайдах рисуется сцена темы колоды — люди за работой, место, продукт в деле, никогда не символ.

Картинка встаёт формой слайда ([`rendering/picture_layouts.py`](verstka/rendering/picture_layouts.py)): обычно полосой во всю высоту у края слайда, текст рядом; круг или скругление — если так говорит шаблон; фон с подложкой — если место занимает почти весь слайд. Картинка не закрывает текст: если рядом с ней слово не помещается в своём кегле, слайд собирается без неё. Картинку, которую Verstka добавила сама и не получила (модель выключена, не ответила, отбраковала надписи), сервис убирает вместе с местом и пересобирает слайд — серой заглушки в готовой колоде нет. Пустое место остаётся только там, где его просил человек: под своё фото или под картинку, которая не нарисовалась (причина — в ходе сборки и в `images.json`).

1. **Промпт.** Сюжет — описание места автором («экран панели управления теплицей»); скилл `image_prompt` пишет его по-английски, зная заголовок слайда и тему колоды, но не переносит в сюжет ни заголовков, ни чисел, ни подписей: Z-Image рисует любой текст из промпта (проверено вживую: заголовок слайда и HEX-коды палитры попадали на изображение). Экран или панель описываются плашками с одним значком и полоской прогресса, график — одной плавной кривой. Без модели текста в промпт идут слова автора. Стиль выбирается по словам описания: фото, иллюстрация или экран. К нему добавляются цвета палитры шаблона только словами, без HEX-кодов, и запрет на любой текст, логотипы и водяные знаки. Длиннее 1000 символов промпт не бывает: сначала уходит общая фраза о слайде, потом конец сюжета — стиль, палитра и запрет на текст остаются всегда.
2. **Палитра.** Изображение сводится к палитре шаблона градиентной картой по яркости: тёмный цвет шаблона, акцент, светлый. Сила — `palette.strength` в `configs/images.yaml`, по умолчанию 0,3. Доля пикселей рядом с цветами палитры (ΔE < 25) записывается в `images.json` и паспорт сборки (`pictures.palette_match`).
3. **Без надписей.** Z-Image рисует буквы и цифры криво, поэтому на картинке их быть не должно. Промпт начинается со слов «A wordless image without a single letter or digit», `image_prompt` не берёт в сюжет предметы с надписями (карты, документы, раскрытые книги, плакаты, вывески, календари, циферблаты с цифрами, формулы), а готовую картинку смотрит VLM (скилл `image_text_check`, около 2 с и 0,03 ₽): есть надпись или её подобие — картинка рисуется заново со строгим промптом (второй раз — иллюстрацией, где надписей почти не бывает), до трёх попыток (`text_check` в `configs/images.yaml`). Если надпись осталась, место остаётся свободным с объяснением («на картинках модель рисовала текст — сгенерируйте ещё раз или вставьте своё изображение»), а отвергнутые попытки описаны в `*-rejected.json`.
4. **Встраивание.** Изображение обрезается по центру точно под пропорции места и становится нативным `p:pic` на месте рамки: та же глубина, геометрия и альтернативный текст. Подпись места уходит. Пропорции места округляются до одной из пяти, поэтому три варианта делят одно изображение.

Бюджет — до 8 разных изображений на сборку, по 3 одновременно, рисуются, пока рендерятся следующие варианты. Экспорт ждёт их не дольше `wait_s` (75 с), иначе место остаётся свободным. Модель изображений одна, поэтому мимолётная помеха её не выключает: минутный лимит Polza пережидается, 429 хостов получает нарастающую паузу (пропуск — только после двух подряд), 402 из-за резерва параллельных запросов ждёт, пока предыдущее изображение освободит резерв, 5xx — свою паузу; всё это — пока до конца бюджета генерации остаётся время на изображение. Если на балансе нет средств (402) или исчерпан дневной лимит модели, модель изображений пропускается на время (до полуночи по Москве для дневного лимита), а места остаются свободными. Одинаковый промпт рисует новое изображение (проверено вживую), поэтому «Сгенерировать другое» работает без seed. Тесты не вызывают моделей: провайдер в них подменён (`tests/unit/test_images*.py`).

## Данные и брендбук (вторая ступень)

Вторая ступень добавила три скилла, но не добавила моделей: те же Qwen3.8-27B (`llm`, `vlm`) и запасная Qwen3.6-27B (профиль Polza), на финале — инференс VK (`qwen38-27b-fp8`). **Числа считает и проверяет код, а не модель**, и это сделано нарочно: профиль, задача, ранжирование видов, агрегация и числа заголовка объяснимы, воспроизводимы, не зависят от шаблона и формата файла и проверяются тестами. Модель берёт на себя три дела, которые код не сделает сам: поймёт, о чём спрашивает бриф (`goal_reader`), напишет связку колоды живым языком (`data_storyteller`) и прочитает картинки страниц PDF (`brandbook_reader`). Ни в одном из них она не выбирает вид диаграммы, не считает и не пишет число, которого нет в фактах.

| | Код ([`verstka/data/`](verstka/data), [`verstka/brand/`](verstka/brand)) | Модель |
|---|---|---|
| Данные | чтение файлов и профиль, аналитическая задача, 2–3 вида визуализации с причинами, агрегация и разбиение, факты и числа, заголовок-вывод по шаблону, подписи осей и единицы, источник, состав и порядок колоды, число слайдов, проверка каждой части цели, самопроверка выводов по сырым строкам, аудит данных, пересборка слайда другим видом | `goal_reader`: что спрашивает бриф — цели над настоящими файлами и колонками, предложения без ответа в данных; `data_storyteller`: название и подзаголовок, контекст из текста, лучшая формулировка заголовка-вывода, заголовок и карточки итога, следующие шаги |
| Брендбук | токены (W3C, Tokens Studio, Style Dictionary, плоский JSON, переменные Figma), текст PDF (HEX, RGB, CMYK, шрифты, поля, сетка, правила), папки и архивы, ссылка Figma, брендированная копия шаблона, расхождения | `brandbook_reader`: роли цветов, шрифты и правила на страницах PDF-гайдлайна |

Вывод, который пишет код, тоже не принимается на веру: до показа каждое число заголовка и подписи и каждое утверждение («впереди», «растёт быстрее всех», «во всех N», «в K из N», ничья, цель, направление «лучше») пересчитывается по сырым строкам файла (`verstka/data/verify.py`: ячейки таблицы и разбор чисел и дат, а не виды анализа; общие с агрегацией — три небольшие функции распознавания колонок). Не подтвердилось — слайд получает заголовок-описание, а причина записывается в «Почему так». В этой проверке модель не участвует.

Чего модель **не делает** ни в одном из трёх скиллов: не выбирает вид диаграммы, не считает и не округляет, не пишет число, которого нет в фактах, не утверждает того, чего нет в фактах слайда (вердикты, уточнения, мера и период числа проверяет код), не называет колонку или файл, которых нет, не добавляет цвет, которого нет в тексте PDF (кроме PDF-скана без текста), не угадывает HEX по пикселям образца. Для других источников брендбука (токены, папка без PDF, Figma) модель не вызывается вовсе; PDF внутри папки или архива читается так же, как отдельный.

### `goal_reader` (`llm`)

Один вызов на сборку для всех файлов вместе, температура 0, ответ до 1 500 токенов, не дольше 30 с (`intent.BUDGET_S`, и не дольше срока генерации). Второй вызов — только если первый вернул пустой объект «{}» (Qwen так отвечает на некоторые брифы при любой температуре); вызова нет вовсе, если в брифе нет вопроса или просьбы. Модель получает бриф и карточки файлов (`dataset_cards`): id, файл и лист, природа данных, число строк, ось времени и её периоды, колонки-периоды, колонки (тип, роль, единица, значения категорий — не больше восьми, диапазон, складывается ли, вес), строки и колонка итога, ориентиры, строки прогноза, задачи, которые данные выдерживают, текст вокруг таблицы. Возвращает `GoalReading`: цели — цитата из брифа, файл, задача, величина, разрез, названные категории, что спрошено (наибольшее, наименьшее, итог, среднее, самый быстрый рост, отрыв, порог выше или ниже, всплеск, выполнение плана, доля N крупнейших, доля названных категорий, колонка против колонки), величина на единицу из двух колонок, агрегация, период, направление «лучше», порог с единицей, с чем сравнить, вопрос «да/нет», уверенность — и предложения брифа, на которые данные ответить не могут, с причиной.

Каждую часть ответа проверяет код (`intent._validate`), отброшенное записывается с причиной (`UnderstoodGoal.dropped`):

| Что | Проверка |
|---|---|
| Цитата | есть в брифе: дословно, после нормализации или как предложение, где её слова составляют не меньше 80 % |
| Файл и колонки | файл существует, колонки существуют, величина числовая |
| Задача | осуществима на этих данных (`task.task_scores`); доли, ключевые значения и распределение сводятся к сравнению, сравнение ряда без категорий — к динамике, динамика по годам колонками — к сравнению; неосуществимая задача становится видимой пометкой «здесь не подходит: …» |
| Агрегация | не сумма долей, средних и уровней; среднее взвешенное требует числовой колонки веса (иначе вес плана, иначе простое среднее) |
| Порог | единица порога — единица колонки; «самый быстрый рост» требует оси времени |
| Период | периоды — периоды данных; диапазон на всю ось — «все данные» |

Цели модели сводятся с целями правил (`_merge`): цель правил, о которой модель промолчала, остаётся; где обе говорят об одном месте брифа и расходятся, берётся цель модели, если её цитаты накрывают цитату правил (кроме хвоста, который ничего не спрашивает: «…, чтобы разобрать на планёрке»), иначе — цель правил. Не осталось ни цели, ни пометки (модель не ответила, не уложилась в срок или ответила неверно) — бриф разбирают правила (`goals=None`), и колода строится так же, как без модели. Цели попадают в план как `goals.Goal`: фраза — цитата брифа (её видит человек в «Почему так»), величина — колонка модели, и код сразу проверяет, что план возьмёт именно эту колонку и этот файл. Числа модель не пишет: она называет колонку и вопрос, а считает и проверяет всё код (`facts`, `verify`).

Ответ кэшируется (LRU на 128 ответов) по хэшу брифа и таблиц, хэшу навыка и ответившей модели: «Цели из текста» в интерфейсе (`POST /api/goals`) и сборка делят один ответ. Цели и вопросы брифа записаны в `run_manifest.json` (`planner.data.goals`, `planner.data.questions`), расход — в `usage`.

**Точность.** Размеченный вручную набор — 168 брифов, 182 цели (брифы проверок conv3 и conv4 и два набора-примера), отложенный набор — 30 новых брифов, 32 цели, размеченные до прогона. Цель верна целиком, когда верны файл, задача, колонка, вопрос, агрегация и период ([`test_data_intent_eval.py`](tests/unit/test_data_intent_eval.py)):

| Набор | Метод | Задача | Колонка | Вопрос | Агрегация | Период | Цель целиком |
|---|---|---|---|---|---|---|---|
| 182 цели | правила | 97,3 % | 89,0 % | 83,5 % | 95,6 % | 90,7 % | 74,7 % |
| 182 цели | модель + проверка кодом | 98,9 % | 98,9 % | 98,4 % | 100 % | 99,5 % | **96,7 %** |
| 32 цели отложенного набора | правила | 71,9 % | 59,4 % | 71,9 % | 71,9 % | 68,8 % | 59,4 % |
| 32 цели отложенного набора | модель + проверка кодом | 100 % | 100 % | 96,9 % | 100 % | 100 % | **96,9 %** |

Числа получены проигрыванием записанных живых ответов Qwen3.8-27B (инференс VK, по одному вызову, 198 вызовов, ни одного сбоя) через текущий код проверок. Тест падает, если подсказки навыка изменились после записи или больше пятой части таблиц читается иначе: ответы тогда нужно записать заново. Размеченный набор служил и для отладки промпта, поэтому честная оценка обобщения — отложенный: на нём верны 31 цель из 32. Вызов на VK: в среднем 1,4 с, медиана 1,3 с, 90-й процентиль 1,9 с, самый долгий 7,9 с; около 4,6 тысячи токенов на входе и 110 на выходе.

### `data_storyteller` (`llm`)

Один вызов на колоду, температура 0,2, ответ до 1 800 токенов, не дольше 90 с (`story.MODEL_BUDGET_S`). Модель получает текст пользователя, черновик (название, подзаголовок, строки контекста), вопросы брифа, текст вокруг таблиц файлов и для каждого слайда с данными его файл, задачу, тему, черновой заголовок, подпись и **факты — единственные числа, которые разрешены в его заголовке**. Возвращает `StoryWriting`: `title`, `subtitle`, `context` (до пяти строк), `headlines` (id слайда и новая формулировка), `summary_title`, `summary` (по строке на карточку итога, до четырёх; каждая — от своего слайда), `next_steps` (до трёх коротких повелительных предложений). Промпт просит название до 70 знаков и заголовки до 100; код принимает названия до 90 знаков, заголовки до 120, строки итога и шагов до 140 знаков (`MAX_CAPTION`), строки контекста до 160. Версия навыка — 1.3.0: промпт требует, чтобы каждое утверждение сохраняло меру, категорию, период и единицу своего факта и не брало уточнений из брифа. Хороший черновой заголовок модель вправе вернуть как есть.

Каждая строка ответа проверяется кодом, и принятая заменяет формулировку кода, а отклонённая нет (`story._tell`):

| Что | Проверка |
|---|---|
| Заголовок слайда | `headline_ok`: каждое число — среди фактов слайда (значение, как его пишет заголовок: 23, а не 22,97); цифры внутри названий из данных («Филиал 1», «25–34», «III кв. 2026») числами не считаются; заголовок не равен теме слайда («Выручка по месяцам» — не вывод) |
| Вывод итога | строка относится ровно к одному слайду данных (`_Attribution.of`): она называет его собственный предмет — слова темы, имени файла и подписей (категорий, рядов, строк, карточек), которых нет у других слайдов, — и не называет предмет другого; все её числа — факты и значения этого слайда; число, привязанное к категории, сказано об этой категории. Строка с предметами двух файлов, строка без видимого предмета и строка вроде «Казань выросла на 41%» (41% — доля Москвы) отклоняются; повтор заголовка слайда целиком принимается как его вывод |
| Заголовок итога, следующие шаги | строка без чисел допустима сама по себе; строка с числами должна относиться к одному слайду данных так же, как вывод итога; шаг должен опираться на предложение самих файлов или на слабое место данных (`answer.step_grounded`), а не на выдумку модели |
| Название и подзаголовок | числа текста пользователя либо, как выше, числа одного слайда данных, если строка называет его предмет |
| Контекст | только числа текста пользователя |
| Смысл (`verstka/data/truth.py`) | слова-вердикты («опережает», «выполнен», «лучше», «самый», «вырос») — только если такой вердикт (или синоним) есть в текстах слайда; уточнения («на посетителя», «за сеанс», «ожидаемая», «всех», «за лето») — только если они есть у слайда, а не в брифе; имена величин и категорий — только со своего слайда; число — со словами своего факта (мера, категория, единица и масштаб: «1 265 тыс. пасс.»); тема вместо ответа в заголовке-ответе и на обложке-ответе не принимается |

Колода берёт новую формулировку только там, где проверка прошла; строка итога заменяет вывод того же слайда одна в одну (остальные карточки остаются); слайд «Что дальше» добавляется, только если не меньше двух шагов опираются на файлы и позволяет число слайдов. Всё записано: `data_story.json` → `rephrased` (что, на каком слайде, было, стало, принято ли и почему нет: «число 45 не из фактов данных»), `written` (ответ модели как он был), сводка `data_story` в `generation.json` и `planner.data` в `run_manifest.json`; вызовы рассказчика попадают в `usage` паспорта запуска. `planned_by` колоды становится `model`, только если принята хотя бы одна формулировка.

**Без модели.** Нет роли `llm` (нет ключа, `--no-llm`, переключатель «Модель пишет тексты слайдов» выключен) — навык не вызывается, колода строится целиком с детерминированными формулировками (`planned_by: rules`): заголовки, подписи, итог из карточек выводов и название остаются, нет только слайда «Что дальше» (его пишет модель). Модель не ответила или не уложилась в 90 с — то же самое, с записью `model_error`. Вид диаграммы и числа от модели не зависят; она меняет слова связки и может добавить слайд «Что дальше».

### `brandbook_reader` (`vlm`)

Сначала PDF читается по тексту (`pypdf`): HEX (а без него RGB и CMYK), роли цветов по словам рядом, шрифты и их замена, поля, сетка, место логотипа, правила, логотипы со страницы о логотипе. Если модель с картинками подключена (роль `vlm`, `use_vlm`), навык получает до шести страниц (`pypdfium2`, шириной не меньше 1600 px: при 1024 px HEX на образцах цвета не читаются; по лучшей странице каждой темы — цвета, шрифты, место логотипа и сетка, правила — и ещё по баллам; скан без текста — шесть страниц поровну) и текстовый черновик, и возвращает `BrandbookReading`: имя бренда, цвета с ролями, шрифты, место логотипа, поля, до восьми правил. Температура 0,1, ответ до 1 200 токенов; запрос один, API даёт всему чтению 150 с.

Что код принимает из ответа (`pdf._merge_reading`): **роль и имя цвета, который уже найден по тексту** (по совпадению HEX), шрифты (если среди них есть шрифт заголовков), место логотипа и поля — только если по тексту они не нашлись, имя бренда (важнее догадки по имени файла, но не заголовка документа), правила — до общего предела. Новый цвет принимается только у PDF-скана без текста, и тогда в предупреждениях стоит «Цвета прочитаны моделью по картинкам страниц (в PDF нет текста) — проверьте HEX».

**Без модели.** Нет роли `vlm` — «Модель для картинок не подключена — PDF прочитан по тексту» в предупреждениях брендбука, и всё остальное работает: разбор по тексту даёт палитру, шрифты, правила и логотипы. Модель ответила ошибкой — «Модель не смогла прочитать страницы — оставил чтение по тексту». Гайдлайн-скан без текста без модели не читается: сервис просит включить модель или загрузить токены JSON. Гайдлайн из примера (`examples/brandbook-vk-cloud/guideline.pdf`) без модели читается целиком: шесть цветов с ролями, два шрифта с заменой Play, правый нижний угол для логотипа, поля 48 px, сетка из 12 колонок, 13 правил и ни одного предупреждения.

### Расход

При сборке — один вызов `goal_reader` (второй только на пустой ответ) и один вызов `data_storyteller` на колоду; при разборе PDF-гайдлайна — один вызов `brandbook_reader`. Изображений вторая ступень не добавляет. «Взгляд дизайнера» и остальные шаги сборки работают на слайдах с данными как на любых других, поэтому стоимость сборки колоды из данных — стоимость обычной сборки плюс два небольших вызова (цели и связка).

## Режим без моделей

Весь пайплайн работает без единого вызова модели (`--no-llm --no-vlm` или отсутствие ключа): классификация только эвристиками, планировщик по заголовкам и абзацам брифа, аудит только детерминированный. Так гарантируются воспроизводимые тесты и демонстрация без сети. Вторая ступень работает так же: файлы с данными читаются, профилируются и показываются кодом, брендбук из токенов, папки и текста PDF читается кодом, а без модели цели разбирают правила, а связку колоды пишет код: название — то, что дал человек, иначе проверенный ответ на главный вопрос брифа или заголовок самих данных (никогда не перечень файлов), контекст — предложения текста, итог — карточки из заголовков-выводов слайдов; слайда «Что дальше» нет.

Без модели работают и входы финальной доводки: план в любом виде раскладывается по пунктам ([`planning/plan_form.py`](verstka/planning/plan_form.py)), длинный документ сжимается правилами — отбором содержательных предложений по частям документа ([`planning/digest.py`](verstka/planning/digest.py)), колода по базе знаний собирается из предложений самих документов с источниками в заметках ([`knowledge/compose.py`](verstka/knowledge/compose.py)), три варианта всё равно различаются формой. Правки словами («таблицей», «крупнее цифры», «короче», «переделай полностью») без модели выполняют правила ([`planning/slide_edit.py`](verstka/planning/slide_edit.py)), и ответ говорит, что сделано по правилам. Без модели не работают: текст по короткой теме без базы знаний (писателю нужна модель), понимание целей моделью (их разбирают правила), «Взгляд дизайнера» и проверка содержания моделью.

## Системные требования

- Python 3.11+, LibreOffice (`soffice`) и poppler (`pdftoppm`) для рендера и PDF.
- Инференс на отборочном этапе — Polza.ai (внешний API-провайдер, что ТЗ разрешает для открытых моделей до 35B), на финале — инференс VK: своя видеокарта не нужна.
- Если поднимать модели самим: Qwen3.8-27B и Qwen3.6-27B — около 56 ГБ видеопамяти в bf16 или около 28 ГБ в fp8 (например, vLLM на A100 80 ГБ); Z-Image — около 21 ГБ в bf16 (6,15B модели + 4B кодировщика текста).
- Расход: одна генерация (три варианта) — по оценке 3–5 ₽ за текст (цены Polza на Qwen3.8-27B — от 18 ₽ за миллион входных и 225 ₽ за миллион выходных токенов в зависимости от хоста) плюс около 3 ₽ за «Взгляд дизайнера» (≈ 40 взглядов и до 8 сравнений на три варианта) и 1,40 ₽ за каждое изображение. Разбор нового шаблона — около 2 вызовов на слайд-образец, результат кэшируется.

## Основная и запасная

В профиле Polza роли `llm` и `vlm` — цепочка из двух моделей: сначала основная, Qwen3.8-27B; если она не может ответить — запасная, Qwen3.6-27B. Обе на одном ключе Polza. Переключение между хостами одной модели Polza делает сама; цепочка нужна для того, что Polza не покрывает: свои лимиты Polza на модель (минутный и дневной), сбой всех хостов модели, исчезнувшая модель, ответ, не прошедший проверку.

Каждое звено, кроме последнего, при неудаче сразу отдаёт запрос следующему. Последнее звено сохраняет короткую паузу и повтор. Сколько звено потом пропускается:

| Ответ Polza | Что происходит |
|---|---|
| 402 `INSUFFICIENT_BALANCE` — на балансе нет средств или исчерпан лимит расходов ключа | звено пропускается 10 минут (пополнение подхватывается быстро) |
| 402, когда баланс занят резервом параллельных запросов (в тексте — зарезервированная сумма, и её возврат покроет запрос: «требуется» ≤ «доступно» + «зарезервировано») | без паузы модели: резерв общий для аккаунта, повтор через несколько секунд (вторым проходом цепочки); резерв, который запрос не покроет, — это пустой баланс или исчерпанный лимит ключа |
| 429 со своим `Retry-After` до 90 с — минутный лимит Polza на модель | модель пропускается до конца минуты, запасная отвечает |
| 429 со своим `Retry-After` длиннее 90 с (до полуночи) — дневной лимит Polza на модель | модель пропускается до полуночи по Москве, запасная отвечает |
| 429 без `Retry-After` или с названием хоста (`metadata.provider_name`) — хосты модели сами ограничили частоту | после двух подряд — 2 минуты |
| 408, 5xx, обрыв соединения | после двух подряд — 1 минута; 503 — не раньше его `Retry-After` |
| 401, отозванный ключ, 403 (не модерация), 404 | 30 минут |
| 403 — модерация отклонила запрос, 400, 413 | без паузы: этот запрос не повторяется, следующий идёт как обычно |
| тайм-аут основной модели | сразу 1 минута, отвечает запасная |
| 503 с `Retry-After` больше 15 с | модель пропускается ровно на это время, раньше запрос не повторяется |
| невалидный JSON после собственных попыток звена | без паузы: модель отвечает, просто неудачно |

«Подряд» считается честно: неудача засчитывается, только если запрос начался после последнего удачного ответа этой модели. Более длинная пауза не сокращается и не переименовывается неудачей, которая была в пути. Таймаут, наступивший потому, что кончился бюджет генерации, модели в вину не ставится.

**Второй проход.** Если хотя бы одна модель не ответила только из-за перегрузки, 5xx, таймаута или минутного лимита, другая и так на паузе, а до конца бюджета осталось не меньше 30 с, цепочка делает ещё один проход через 3–5 с. Если обе на паузе, но пауза одной кончается в пределах 30 с (минутный лимит), цепочка дожидается её. Не больше трёх проходов. Только когда не ответила ни одна модель, шаг уходит в свой детерминированный вариант, а в предупреждениях варианта перечислены причины по каждой модели: «all model links failed: [Qwen3.8-27B] qwen/qwen3.8-27b: per-minute request cap …; [Qwen3.6-27B] …».

Паузы у каждой пары «аккаунт + модель» свои (`verstka/providers/status.py`): лимит основной модели не блокирует запасную. Роли `llm` и `vlm` делят их. Паузы живут в памяти процесса: перезапуск сервера их сбрасывает.

**Какая модель ответила.** `CompletionResult.model` и `label` — модель, которая действительно ответила. Состояние моделей для интерфейса — `verstka.providers.status.snapshot(реестр)` (`GET /api/models/status`): по каждой модели `model`, `label`, `host`, `state`, `available`, `until`, `last_ok`, `last_error` (коротко, ключи замаскированы), `roles`. Состояния: `ok`, `unknown`, `congested` (хосты перегружены, 5xx, таймаут, резерв баланса), `rate` (минутный лимит), `quota` (дневной лимит, до полуночи по Москве), `no_credits` (402), `auth`, `missing`, `error`, `off` (нет ключа). Интерфейс человеку не пишет ни про деньги, ни про ключи: «Модель недоступна», «Соберите ещё раз через минуту», «…после полуночи по московскому времени»; что исправить владельцу сервера («На балансе Polza нет средств или исчерпан лимит расходов ключа…») — только во всплывающей подсказке.

## Финал: инференс VK

На финале по ТЗ обязателен инференс VK: чтение текста и изображений идёт через Qwen3.8-27B на платформе организаторов. Профиль — [`configs/models.vk.yaml`](configs/models.vk.yaml): та же Qwen3.8-27B (`qwen38-27b-fp8`) первым звеном цепочки, до 8 запросов одновременно, бюджет модели на генерацию 210 с. Если VK не отвечает (недоступен, «500 congested upstream», таймаут), в том же запросе отвечает та же Qwen3.8-27B на Polza, затем Qwen3.6-27B на Polza: звено VK спрашивается не больше двух раз с тайм-аутом 90 с, а после двух неудач подряд цепочка минуту шлёт запросы сразу на Polza (живая проверка 19.10: VK ответил 500 — ответ Polza через 4,2 с). Без `POLZA_API_KEY` звенья Polza выключены и работает только VK. Какая модель ответила, пишется в `run_manifest.json` и видно в `GET /api/models/status`. Ключи `VK_INFERENCE_API_KEY` и `VK_PROJECT_ID` лежат в `.env` (адрес инференса уже записан в профиле); когда заданы оба, профиль VK выбирается сам, без других настроек и без правки кода — по умолчанию без ключей VK остаётся `configs/models.yaml` (Polza). Картинки — по-прежнему Z-Image через Polza (`POLZA_API_KEY`, тот же вызов, что в основном профиле), пока у VK нет собственной модели изображений: без ключа Polza места под изображения остаются свободными. Если VK предоставит открытую модель изображений (OpenAI-совместимый `POST /images/generations`), её id указывают в `VK_T2I_MODEL`: она спрашивается первой, Z-Image отвечает вслед за ней. Строка `VERSTKA_MODELS=configs/models.vk.yaml` (или `configs/models.yaml`) в `.env` и ключ `--models` у `verstka serve` выбирают профиль принудительно и важнее ключей VK; сервер один раз пишет в журнал, какой профиль выбран и почему (без значений ключей); если `VERSTKA_MODELS` выбирает не профиль VK, хотя оба ключа VK заданы, в журнал идёт предупреждение — уберите её из `.env`, чтобы работал VK. Инференс VK не сообщает стоимость запроса, поэтому `usage.cost_rub` для него пуст. Рассуждения там выключаются флагом шаблона чата (`chat_template_kwargs: {enable_thinking: false}`) и переключателем `/no_think` в системном сообщении; проверка — `scripts/vk_smoke.py`.

Звено цепочки, оставшееся последним (например, VK без ключа Polza), ведёт себя как одна модель: до 3 попыток с паузами 2 и 4 с; 429 хостов — пауза 5–8 с и ещё одна попытка, после двух подряд модель пропускается 2 минуты; минутный лимит пережидается; 402 / 401 / 403 / 404 на Polza сообщаются сразу (на инференсе VK — после попыток), затем модель пропускается не дольше минуты.

## Тесты

Тесты герметичны: `tests/conftest.py` ставит `VERSTKA_NO_DOTENV=1` (ключ из `.env` в тесты не попадает) и `VERSTKA_NO_CATALOG=1` (каталог Polza не читается), убирает из окружения `POLZA_API_KEY`, `VERSTKA_MODELS`, `VK_INFERENCE_API_KEY`, `VK_INFERENCE_BASE_URL` и `VK_T2I_MODEL` (`VK_PROJECT_ID` остаётся: без ключа профиль VK не включается) и обрывает любое соединение не с локальной машиной. Провайдеры в тестах подменены: ни один тест не вызывает настоящую модель. Исключение — записанные ответы: ответы Qwen3.8-27B на цели брифов (`tests/fixtures/intent/answers.json`) проигрываются через те же проверки, что в сборке, а ответы, на которых раньше выходили ложные выводы (цели и переписанные строки связки), записаны прямо в `tests/unit/test_data_truth.py`; обращения к сети нет.
